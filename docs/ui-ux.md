# การออกแบบ UI/UX

หลักการที่ทุกหน้าจอใช้ร่วมกัน ใช้ตรวจงานก่อนส่งทุกครั้งที่เพิ่มหรือแก้หน้าจอ

## ผู้ใช้ของเรา

| ผู้ใช้ | ใช้บนอะไร | ต้องการอะไรจากหน้าจอ |
|---|---|---|
| เจ้าหน้าที่ | คอมพิวเตอร์เป็นหลัก เปิดทั้งวัน | เห็นงานที่ต้องทำตอนนี้ ตอบเร็ว ไม่ต้องคลิกหลายชั้น |
| เจ้าขององค์กร | คอมพิวเตอร์และมือถือ | เห็นภาพรวมทีม ตั้งค่าเองได้โดยไม่ต้องรู้เรื่องเทคนิค |
| ลูกค้า | มือถือเป็นหลัก | รู้ว่ากำลังคุยกับใคร เรื่องไปถึงไหน และต้องรอนานเท่าไร |
| ผู้ดูแลแพลตฟอร์ม | คอมพิวเตอร์ | รู้ว่าอะไรเสียและต้องแก้ที่ไหน |

## ภาษา

### คำบนหน้าจอ

- **ภาษาไทยทั้งหมด** ชื่อเฉพาะใช้ตามจริง เช่น LINE, Facebook, Passkey
- **ไม่ใช้ศัพท์เทคนิคภาษาอังกฤษกับเจ้าขององค์กรและลูกค้า** เช่น เขียนว่า "ค่ากลาง" แทน median หรือเขียนว่า "9 ใน 10 เคส" แทน P90 ถ้าจำเป็นต้องมีศัพท์ ให้มีคำอธิบายภาษาไทยอยู่ข้างกัน
- **ห้ามใช้ขีดยาว** (`—`) ในข้อความบนหน้าจอ คนไทยไม่ใช้
- **ลูกค้าและทีมงานเห็นคำไม่เหมือนกัน** เช่น สถานะเคส `pending_customer` ทีมงานเห็น "รอลูกค้า" แต่ลูกค้าเห็น "รอข้อมูลจากคุณ" คำของลูกค้าอยู่ใน `customerStates` ของ `lib/labels.ts`
- **ข้อความ error บอกสิ่งที่ต้องทำ** ไม่ใช่รหัสข้อผิดพลาด เช่น "แนบไฟล์ได้สูงสุด 3 ไฟล์"
- **ตัวอย่างในช่องกรอก (placeholder) ต้องเป็นกลาง** ห้ามนำตัวอย่างที่ผู้ใช้หรือลูกค้าเคยยกมาไปใส่เป็น placeholder

### เอกสาร

เอกสารใน `docs/` ห้ามใช้ขีดยาว (`—` และ `–`) และจุดกึ่งกลาง (`·`) ในประโยค แยกหัวข้อให้ชัด เรื่องหนึ่งอยู่ในที่เดียว

### วันเวลาและตัวเลข

- วันที่ใช้ `Intl.DateTimeFormat('th-TH')` เช่น "26 ก.ย."
- ระยะเวลาเขียนแบบคนอ่าน เช่น "3 ชม. 20 นาที" หรือ "2 วัน 4 ชม."
- ตัวเลขที่มาจากข้อมูลน้อยเกินไปให้แสดงเป็นสีจาง พร้อมบอกว่ายังใช้ตัดสินไม่ได้
- ตัวเลขคาดการณ์แสดงเป็นช่วง ไม่ใช่ตัวเลขเดียว และบอกว่าแม่นแค่ไหน

## การจัดหน้า

- **ห้ามมีแถบเลื่อนแนวนอนทั้งหน้า** ทุกหน้าต้องใช้ได้ที่ความกว้าง 390 px (มือถือ) ตารางกว้างให้เลื่อนเฉพาะในกรอบของตาราง หรือเปลี่ยนเป็นการ์ดบนจอเล็ก
- **ห้ามมีแถบเลื่อนที่ไม่จำเป็น** เช่น กล่องที่ความสูงคงที่ทั้งที่เนื้อหาพอดีอยู่แล้ว
- **ไม่อัดแน่น** เว้นระยะให้หายใจได้ ถ้าเบียดให้ขึ้นบรรทัดใหม่หรือเปลี่ยนเป็นหลายแถว
- **การ์ดจัดตามความกว้างของตัวเอง** ใช้ container query เมื่อการ์ดวางข้างแถบเมนู เพราะจอแท็บเล็ตอาจทำให้การ์ดแคบเท่ามือถือ
- **ตัวเลือกหลายอันจัดให้แถวเต็ม** เช่น 8 ตัวเลือกเป็น 2 แถว แถวละ 4 ไม่ให้เหลือตัวเดียวโดด ๆ ในแถวสุดท้าย
- **พื้นที่กดอย่างน้อย 44 px** สำหรับปุ่มที่ใช้บนมือถือ

## สีและธีม

- สีทั้งหมดกำหนดเป็นตัวแปร CSS (token) ใน `src/styles/base.css` เช่น `--ink`, `--muted`, `--line`, `--soft`, `--green`, `--amber`, `--red`
- ธีมมี 4 แบบ คือ ขาว ครีม ดาร์ก และดำ (`src/styles/themes.css`) ธีมเปลี่ยนเฉพาะค่าของ token จึงต้องใช้ token เสมอ ห้ามเขียนสีตรงถ้าไม่จำเป็น
- ธีม ขนาดตัวอักษร (80% ถึง 150%) และฟอนต์ (Sarabun หรือ Noto Sans Thai) จำไว้ในเบราว์เซอร์ และถูกตั้งก่อนหน้าจอวาด หน้าจอจึงไม่กระพริบเป็นสีขาวตอนเปิด
- **ตรวจทุกหน้าจอในธีมมืดด้วย** รูปที่วาดสำหรับพื้นขาว เช่น โลโก้ ต้องมีพื้นขาวรองรับเมื่ออยู่บนพื้นมืด
- **ห้ามใช้สีม่วงเป็นสีเน้น**
- **ห้ามปุ่มหรือตัวควบคุมสีเทาจาง** ตัวหนังสือและขอบต้องมีความต่างของสีพอให้อ่านง่าย

## สิ่งที่ไม่ใช้

| ไม่ใช้ | เหตุผล |
|---|---|
| ขีดเส้นใต้เมื่อชี้เมาส์ (ทุกกรณี) | รก และเลื่อนสายตา |
| แถบสีด้านข้างของการ์ด | ดูเป็นการตกแต่งที่ไม่สื่อความหมาย |
| ป้ายรูปลูกโลก | ไม่สื่ออะไรกับผู้ใช้ |
| `alert`, `confirm`, `prompt` ของเบราว์เซอร์ | ใช้กล่องโต้ตอบของแอปแทน |
| inline style (`style={...}`) | CSP ไม่อนุญาต ดูหัวข้อถัดไป |

## ข้อจำกัดจาก Content-Security-Policy

หน้าเว็บจริงไม่อนุญาต inline style ความกว้างหรือความสูงที่คำนวณตอนรันจึงต้องทำด้วยวิธีเหล่านี้

- แท่งกราฟและแถบความคืบหน้าใช้ `<progress>`
- กราฟที่ซับซ้อนวาดด้วย SVG เพราะขนาดเป็น attribute ไม่ใช่ style
- ตำแหน่งของเมนูลอยตั้งผ่าน `element.style.setProperty` (CSSOM)
- ตัวเลือกสีใช้ชุดที่เตรียมไว้เป็น class ไม่ให้เลือกสีอิสระ

## ส่วนประกอบที่ใช้ร่วมกัน

| ส่วนประกอบ | ใช้เมื่อ |
|---|---|
| `Form` และ `fields` | ทุกฟอร์ม ข้อความผิดพลาดขึ้นใต้ช่องเป็นภาษาไทยหลังออกจากช่องหรือกดส่ง มีดอกจันที่ช่องบังคับ และปุ่มรูปตาที่ช่องรหัสผ่าน |
| `Combobox` | รายการที่ยาวได้ เช่น ลูกค้า สมาชิก พิมพ์ค้นหาได้ ใช้แป้นลูกศรได้ |
| `Dialogs` | modal สำหรับฟอร์ม และ sheet สำหรับคำถามที่ซ้อนบน modal กดพื้นที่มืดหรือ Escape เพื่อปิด ฟอร์มที่ยังไม่บันทึกกันการปิดได้ |
| `Toast` | ข้อความสั้นด้านล่าง หายเองใน 4.5 วินาที error เป็นสีแดง |
| `EmptyState`, `ErrorState`, `PageLoading` | ไม่มีข้อมูล โหลดไม่สำเร็จ (มีปุ่มลองใหม่) และกำลังโหลด |
| `FilterPill`, `Pager` | แถบตัวกรองและการแบ่งหน้าแบบเดียวกันทุกหน้าจอ |

## พฤติกรรมที่คาดหวัง

- **บอกเหตุผลเสมอ** ปุ่มที่ใช้ไม่ได้ต้องบอกว่าทำไม หรือพาไปที่ต้องทำก่อน แทนการปิดปุ่มเป็นสีเทา
- **การลบต้องย้อนได้หรือยืนยันก่อน** ของที่ลบส่วนใหญ่ไปอยู่ในถังขยะ 30 วัน การลบถาวรต้องพิมพ์ยืนยัน
- **ไม่เดาแทนผู้ใช้** เช่น ไม่แยกชื่อกับนามสกุลอัตโนมัติจากชื่อเดิม
- **ไม่หลอกผู้ใช้ด้วยตัวเลข** ข้อมูลไม่พอให้บอกว่าไม่พอ แทนการแสดงศูนย์หรือค่าที่ดูดี
- **หน้าที่อัปเดตเองต้องไม่ทำงานที่ผู้ใช้พิมพ์อยู่หาย** และไม่เลื่อนตำแหน่งที่อ่านอยู่

## การเข้าถึง

- ทุกปุ่มที่มีแต่ไอคอนต้องมี `aria-label`
- สิ่งที่ลากวางได้ต้องทำด้วยแป้นพิมพ์ได้ด้วย
- กราฟมีตัวเลขในตารางหรือ tooltip สำหรับคนที่อ่านแท่งกราฟไม่ได้
- ภาพเคลื่อนไหวหยุดเมื่อผู้ใช้ตั้งค่าลดการเคลื่อนไหวในระบบปฏิบัติการ

## หน้าช่วยเหลือขององค์กร

หน้าที่ลูกค้าขององค์กรเปิด (`/support/<code>`) ต้องบอกให้ชัดว่ากำลังติดต่อใคร จึงมีแบนเนอร์ขององค์กรอยู่บนสุด และชื่อ Bookdose อยู่เป็นบรรทัดเล็กท้ายหน้า ดู [หน้าช่วยเหลือและแชทผู้เยี่ยมชม](features/support-page-and-guest-chat.md)
