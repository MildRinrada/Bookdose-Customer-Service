# รายงาน

รายงานการบริการ (`/reports`) ตอบว่าช่วงที่เลือก ทีมทำงานได้ดีแค่ไหน ลูกค้าพอใจหรือไม่ งานมาจากไหน ข้างหน้าจะมีงานเท่าไร และคนพอหรือไม่ ทุกคนในองค์กรเปิดได้ เจ้าหน้าที่เห็นเฉพาะข้อมูลของทีมตัวเอง

รายงานส่วนใหญ่คำนวณในเบราว์เซอร์จากรายการเคส (`GET /api/tickets`) ซึ่ง API กรองตามสิทธิ์มาแล้ว ส่วนที่รายการเคสบอกไม่ได้มาจาก `GET /api/reports/extras` และวันทำงานของทีมมาจาก `GET /api/reports/staffing` (เจ้าขององค์กร)

## ตัวกรอง

- ช่วงเวลา: 7 วัน 30 วัน 90 วัน 1 ปี หรือเลือกวันเอง (ไม่เกิน 1 ปี)
- ทีม และผู้รับผิดชอบ
- ทุกตัวเลขเทียบกับช่วงก่อนหน้าที่ยาวเท่ากัน
- วันและชั่วโมงนับตามเวลาของเครื่องผู้ดู

## ส่วนของรายงาน

| ส่วน | บอกอะไร |
|---|---|
| ตัวเลขสรุป | เคสทั้งหมด ยังดูแลอยู่ เวลาตอบครั้งแรก (ค่ากลาง) และสัดส่วนที่ตอบทัน SLA พร้อมเป้า ถ้าตั้งไว้ |
| เป้าหมาย | ตัวเลขที่ตั้งเป้าไว้ ถึงเป้าหรือยัง และหลุดเป้าช่วงไหน ดู [เป้าหมาย](#เป้าหมาย) |
| แถบเตือน | จำนวนเคสที่เกิน SLA ในช่วงนี้ กดแล้วเปิดรายการ |
| ปริมาณเคสต่อวัน | กราฟรายวัน พร้อมไฮไลต์วันที่ผิดปกติ |
| พยากรณ์จำนวนเคส | ช่วงที่คาดใน 14 วันข้างหน้า และทดสอบความแม่นย้อนหลัง |
| คนที่ต้องใช้แต่ละวัน | เจ้าขององค์กร: แต่ละวันข้างหน้าต้องใช้กี่คน มีกี่คน และวันไหนคนไม่พอ |
| เวลาตอบกลับครั้งแรก | ค่ากลาง 9 ใน 10 เคส ค่าเฉลี่ย ทันกำหนด และการกระจายเป็นช่วงเวลา |
| เวลาแก้ไขจนเสร็จ | ตัวเลขชุดเดียวกัน สำหรับเคสที่แก้ไขเสร็จในช่วงนี้ |
| ระหว่างการคุย | รอคำตอบถัดไป และแก้จบในครั้งเดียว ดู [ระหว่างการคุย](#ระหว่างการคุย) |
| อารมณ์ลูกค้า | สัดส่วนเคสที่ลูกค้าไม่พอใจ รายช่วง และเรื่องที่ไม่พอใจบ่อย ดู [อารมณ์ลูกค้า](#อารมณ์ลูกค้า) |
| ความพึงพอใจ (CSAT) | คะแนนเฉลี่ย จำนวนแต่ละดาว คะแนนรายสัปดาห์ และความคิดเห็น (คะแนนต่ำสุดก่อน) |
| ความเร็วกับความพอใจ | คะแนนของลูกค้าแยกตามว่ารอนานแค่ไหน |
| วิเคราะห์แยกตามมุม | ตารางแยกมิติที่เลือกเอง |
| เคสค้าง | เคสที่ยังเปิดอยู่ แยกตามอายุ และเคสที่รอนานที่สุด |
| ภาระงาน | เคสที่เปิดอยู่ของแต่ละคน และคนที่ถือมากกว่าค่าเฉลี่ยของทีมมาก |
| การเปิดซ้ำ | สัดส่วนเคสที่กลับมาหลังปิดแล้ว |
| สถานะและความเร่งด่วน | สัดส่วนของเคสในช่วงนี้ |
| เคสตามป้าย | ป้ายที่พบมากที่สุดในช่วงนี้ เทียบกับช่วงก่อนหน้า และจำนวนเคสที่ติดป้ายแล้ว |
| ช่วงเวลาที่ลูกค้าติดต่อ | แผนภาพวันในสัปดาห์กับชั่วโมง |
| AI และคลังความรู้ | เจ้าขององค์กร: Chatbot ตอบจบเองกี่ครั้ง ส่งต่อคนกี่ครั้งและเพราะอะไร ผู้ช่วย AI ได้ถูกใจกี่ส่วน ไม่ถูกใจเพราะอะไร และทีมกดทำเลยตามที่เสนอกี่ส่วน (ไม่แสดงชื่อคนให้คะแนน) และบทความที่ทีมใช้หรือให้คะแนนว่าไม่ช่วย |
| ผลงานตามผู้รับผิดชอบ | เคสทั้งหมด ยังดูแลอยู่ เกิน SLA เวลาตอบ และสัดส่วนที่ทัน |

## เป้าหมาย

เจ้าขององค์กรตั้งได้ที่ปุ่ม **ตั้งเป้าหมาย** หรือ **แก้เป้าหมาย** บนการ์ดเป้าหมาย ตั้งเฉพาะข้อที่ต้องการ ข้อที่เว้นว่างคือไม่ตั้ง

| ตัวเลข | เป้าแบบ | นับอย่างไร |
|---|---|---|
| ตอบทัน SLA | อย่างน้อย (%) | เคสที่เปิดในช่วงนี้และตอบแล้ว |
| ตอบครั้งแรก (ค่ากลาง) | ไม่เกิน (นาที) | เคสที่เปิดในช่วงนี้และตอบแล้ว |
| รอคำตอบถัดไป (ค่ากลาง) | ไม่เกิน (นาที) | ดู [ระหว่างการคุย](#ระหว่างการคุย) |
| แก้จบในครั้งเดียว | อย่างน้อย (%) | ดู [ระหว่างการคุย](#ระหว่างการคุย) |
| คะแนนความพึงพอใจ | อย่างน้อย (1 ถึง 5) | คำตอบแบบประเมินที่ได้รับในช่วงนี้ |
| เปิดซ้ำ | ไม่เกิน (%) | เหมือนการ์ดการเปิดซ้ำ |
| ลูกค้าไม่พอใจ | ไม่เกิน (%) | ดู [อารมณ์ลูกค้า](#อารมณ์ลูกค้า) |

- **ทั้งองค์กรและรายทีม** เลือก "เป้าหมายของ" ในฟอร์ม ทีมตั้งเฉพาะข้อที่ต่างจากองค์กร ข้อที่เว้นว่างใช้เป้าขององค์กร
- **เป้าที่ใช้** ตามทีมที่เลือกในตัวกรอง ถ้าไม่เลือกทีมใช้เป้าขององค์กร เจ้าหน้าที่เห็นเป้าของทีมตัวเอง
- **การ์ดเป้าหมาย** แต่ละข้อบอกตัวเลขของช่วงนี้ ถึงเป้าหรือยังไม่ถึง และช่องรายช่วง (รายวันสำหรับช่วงไม่เกิน 14 วัน รายสัปดาห์ถึง 120 วัน แล้วราย 30 วัน) ช่องสีแดงคือช่วงที่ไม่ถึงเป้า
- **ตัวเลขสรุป** ตอบทัน SLA เป็นสีเขียวเมื่อถึงเป้า และบอกเป้าไว้ใต้ตัวเลข ถ้าไม่ได้ตั้งเป้า ใช้ 90% เหมือนเดิม
- ตัวเลขทุกข้อนับแบบเดียวกับการ์ดอื่นในหน้านี้ จึงตรงกันเสมอ
- เป้าเก็บในการตั้งค่าขององค์กร (`report_goals`) บันทึกผ่าน `POST /api/reports/goals` เฉพาะเจ้าขององค์กร และลงประวัติการทำงาน

## ระหว่างการคุย

เวลาตอบครั้งแรกบอกแค่คำตอบแรก ถ้าลูกค้าถามต่อแล้วรอ 2 วัน ตัวเลขนั้นยังดูดีอยู่ การ์ดนี้จึงนับสิ่งที่เกิดหลังคำตอบแรก

- **รอคำตอบถัดไป** นับทุกครั้งที่ลูกค้าเขียนมาหลังทีมตอบครั้งแรกแล้ว ตั้งแต่ข้อความแรกของรอบนั้น จนถึงคำตอบถัดไปของทีม แสดงค่ากลาง ค่าที่ 9 ใน 10 ครั้งได้คำตอบภายใน และจำนวนครั้งที่รอ เคสที่เปิดในช่วงนี้เท่านั้น คำตอบของบอตและข้อความระบบไม่นับเป็นคำตอบ ครั้งที่ยังรออยู่ยังไม่นับ
- **แก้จบในครั้งเดียว** ของเคสที่แก้ไขเสร็จในช่วงนี้และทีมตอบอย่างน้อยหนึ่งครั้ง สัดส่วนที่ทีมตอบครั้งเดียวแล้วจบ และไม่เคยถูกเปิดซ้ำ
- เทียบกับช่วงก่อนหน้าที่ยาวเท่ากัน

## อารมณ์ลูกค้า

ข้อมูลนี้มาถึงก่อนคะแนนความพึงพอใจ ซึ่งลูกค้าส่วนใหญ่ไม่ได้ตอบ

- **ลูกค้าไม่พอใจ** สัดส่วนเคสที่เปิดในช่วงนี้ ที่ลูกค้าไม่พอใจหรือโกรธอย่างน้อยหนึ่งข้อความ อ่านจากคำในข้อความ และจาก AI เมื่อเปิด [อ่านอารมณ์ลูกค้าด้วย AI](ai.md#อ่านอารมณ์ลูกค้า) ข้อความที่ใจเย็นลงทีหลังไม่ลบว่าเคยไม่พอใจ
- **โกรธมาก** จำนวนเคสที่ลูกค้าโกรธมาก
- **รายช่วง** ช่องสีแดงเมื่อเกินเป้า (ถ้าตั้งไว้)
- **ลูกค้าไม่พอใจบ่อยในเรื่องไหน** 5 กลุ่มที่สัดส่วนสูงสุด จากหมวดเรื่อง ป้ายเคส และช่องทาง นับเฉพาะกลุ่มที่มีอย่างน้อย 3 เคส

## ตัวเลขที่นับจากข้อความ

รอคำตอบถัดไป แก้จบในครั้งเดียว และอารมณ์ลูกค้า มาจาก `GET /api/reports/extras` (`case_stats`) เป็นตัวเลขต่อเคส ไม่มีเนื้อความ เซิร์ฟเวอร์นับให้เฉพาะเคสที่ผู้ดูเห็นได้ และที่เปิด แก้ไขเสร็จ หรือถูกเปิดซ้ำ ในช่วงที่เลือกหรือช่วงก่อนหน้า ระหว่างโหลด การ์ดบอกว่ากำลังนับ

## เวลาตอบและเวลาแก้ไข

แสดงค่ากลางและค่าที่ 9 ใน 10 เคสทำได้ คู่กับค่าเฉลี่ย เพราะเคสค้างนานไม่กี่เคสดึงค่าเฉลี่ยจนดูแย่เกินจริง ค่าเฉลี่ยจึงไม่แสดงเดี่ยว ๆ

การกระจายของเวลาตอบครั้งแรกแบ่งเป็น ภายใน 15 นาที, 15 ถึง 60 นาที, 1 ถึง 4 ชม., 4 ถึง 24 ชม. และเกิน 1 วัน

## วันที่ผิดปกติ

แต่ละวันในกราฟเทียบกับวันเดียวกันของสัปดาห์ใน 4 สัปดาห์ก่อนหน้า (วันจันทร์เทียบกับวันจันทร์ เพราะแต่ละวันมีรูปแบบของตัวเอง)

- **มากกว่าปกติ** ตั้งแต่ 2 เท่าของค่ากลาง และเกินอย่างน้อย 3 เคส
- **น้อยกว่าปกติ** วันที่ปกติมีหลายเคส แต่เหลือไม่ถึงหนึ่งในสาม อาจเป็นวันหยุด หรือช่องทางติดต่อมีปัญหา
- วันนี้ยังไม่จบ จึงไม่ถูกเรียกว่าน้อยผิดปกติ
- ต้องมีข้อมูลย้อนหลังอย่างน้อย 3 สัปดาห์ องค์กรใหม่จึงไม่ถูกบอกว่าทุกวันผิดปกติ

## พยากรณ์จำนวนเคส

คาดการณ์เคสใหม่ 14 วันข้างหน้า นับจากวันนี้เสมอ ไม่ขึ้นกับช่วงวันที่ที่เลือก ใช้ตัวกรองทีมได้

**แสดง**

- จำนวนเคส 7 วันข้างหน้าเทียบกับ 7 วันที่ผ่านมา วันที่น่าจะหนักที่สุด และแนวโน้มต่อสัปดาห์
- กราฟ: ครึ่งซ้ายคือ 14 วันที่ผ่านมา เคสจริงเทียบกับช่วงที่ทำนายไว้ วันที่หลุดช่วงเป็นสีส้ม ครึ่งขวาคือช่วงที่คาดใน 14 วันข้างหน้า
- รายวัน: ช่วงที่คาด เช่น "40-55 เคส" และ 3 ชั่วโมงที่น่าจะหนักที่สุดพร้อมจำนวนโดยประมาณ ใช้จัดคนเข้ากะ

**วิธีคิด** อธิบายได้ในประโยคเดียว

1. สัดส่วนปกติของแต่ละวันในสัปดาห์ จาก 8 สัปดาห์ล่าสุด เมื่อมีข้อมูลตั้งแต่ 5 สัปดาห์ ตัดสัปดาห์ที่สูงสุดและต่ำสุดทิ้ง วันที่พุ่งวันเดียวจึงไม่ดึงผล
2. เส้นแนวโน้มของยอดรายสัปดาห์ ใช้ค่ากลางของความชันระหว่างทุกคู่สัปดาห์ สัปดาห์แปลก ๆ สัปดาห์เดียวจึงไม่ทำให้เส้นเอียง แล้วลากต่อไปข้างหน้าแบบค่อย ๆ แบนลง เพราะการเพิ่มขึ้นมักไม่ต่อเนื่องตลอดไป
3. ช่วงที่ทำนายตั้งให้เคสจริงตกอยู่ในช่วงราว 8 ใน 10 วัน วันที่เคสเยอะแกว่งมากกว่าวันที่เคสน้อยตามธรรมชาติของข้อมูลนับ

**ทำนายแม่นแค่ไหน** ระบบลองทำนาย 14 วันที่ผ่านมาโดยใช้เฉพาะเคสก่อนหน้านั้น แล้วบอก

- พลาดเฉลี่ยวันละกี่เคส และคิดเป็นกี่เปอร์เซ็นต์ของเคสจริง
- เคสจริงอยู่ในช่วงที่ทำนายกี่วันจาก 14 วัน
- แม่นกว่าหรือแย่กว่าการเดาว่า "เท่าสัปดาห์ก่อน"

ถ้าผลแย่ มีคำเตือนให้ใช้ตัวเลขเป็นแนวทางคร่าว ๆ

**ข้อจำกัด**

- ต้องมีเคสย้อนหลังอย่างน้อย 6 สัปดาห์ (4 สัปดาห์ไว้เรียนรู้ และ 2 สัปดาห์ไว้ทดสอบ) ถ้าไม่ถึง การ์ดบอกว่าต้องรออีกกี่วัน
- ไม่รู้ล่วงหน้าเรื่องวันหยุด แคมเปญ หรือระบบล่ม

## คนที่ต้องใช้แต่ละวัน

เฉพาะเจ้าขององค์กร อยู่ใต้การ์ดพยากรณ์ ใช้ตัวกรองทีมได้

**แต่ละวันบอก** เคสที่คาด ต้องใช้กี่คน มีกี่คนที่ทำงานวันนั้น และผล คือ พอ พอดี ขาดกี่คน หรือองค์กรปิด พร้อมรายชื่อคนที่ไม่อยู่และเหตุผล (ลา หรือไม่ใช่วันทำงาน)

**วิธีคิด**

1. **คนหนึ่งปิดได้วันละกี่เคส** จากเคสที่ปิดใน 4 สัปดาห์ล่าสุด หารด้วยจำนวนวันที่แต่ละคนปิดเคสอย่างน้อยหนึ่งเคส วันหยุดจึงไม่ถูกนับเป็นวันที่ไม่ได้ทำงาน ต้องมีอย่างน้อย 10 วันทำงานรวมกัน
2. **ต้องใช้กี่คน** คือเคสที่คาดหารด้วยตัวเลขข้อ 1 ปัดขึ้น แสดงเป็นช่วง ตัวแรกคิดจากจำนวนที่น่าจะเป็นที่สุด ตัวหลังคิดจากขอบบนของช่วงพยากรณ์
3. **มีกี่คน** นับเจ้าหน้าที่ทุกคน และเจ้าขององค์กรที่ปิดเคสเองใน 4 สัปดาห์ล่าสุด คนที่ลาในวันนั้นหรือวันนั้นไม่ใช่วันทำงานของเขาไม่นับ วันหยุดพิเศษขององค์กรปิดทั้งวัน (เมื่อองค์กรใช้เวลาทำการ)
4. **ผล** ขาดเมื่อคนน้อยกว่าตัวแรก พอดีเมื่อพอสำหรับตัวแรกแต่ไม่พอสำหรับตัวหลัง

**ข้อจำกัด**

- วันลาและเวลาทำงานมาจากตั้งค่าบัญชีของแต่ละคน คนที่ยังไม่ได้ตั้งเวลาทำงานนับว่าทำงานทุกวันที่องค์กรเปิด (หรือทุกวันถ้าองค์กรไม่ได้ตั้งเวลาทำการ) การ์ดบอกว่ามีกี่คน
- ไม่รวมเคสที่ค้างอยู่ตอนนี้ นับเฉพาะเคสใหม่ที่คาดว่าจะเข้ามา
- เหตุผลการลาไม่ถูกส่งมาที่หน้านี้ บอกแค่ว่าลา

## ความเร็วกับความพอใจ

แบ่งเคสที่ลูกค้าให้คะแนนตามเวลาตอบครั้งแรก หรือเวลาแก้ไขเสร็จ แล้วดูคะแนนของแต่ละกลุ่ม เช่น "ลูกค้าที่ได้คำตอบแรกภายใน 15 นาที ให้คะแนนเฉลี่ย 4.6 ส่วนที่รอเกิน 1 วัน ให้ 3.2" ใช้ตั้งเป้า SLA จากข้อมูลจริง

ตัวเลขนี้บอกว่าความเร็วกับคะแนนไปด้วยกันแค่ไหน แต่ไม่ได้พิสูจน์ว่าความเร็วเป็นสาเหตุ เพราะเรื่องยากมักทั้งใช้เวลานานและได้คะแนนต่ำ

## วิเคราะห์แยกตามมุม

เลือกมิติที่จะแยก แล้วดูทุกตัวเลขพร้อมกันเป็นคอลัมน์

**มิติ:** ช่องทาง หมวดเรื่อง ป้ายเคส ทีม ความเร่งด่วน ผู้รับผิดชอบ วันที่ลูกค้าติดต่อ ช่วงเวลาที่ลูกค้าติดต่อ และ[ช่องข้อมูลเพิ่มเติม](tickets.md#ช่องข้อมูลเพิ่มเติม)แบบตัวเลือกและแบบติ๊ก

ป้ายเคสแสดงเมื่อองค์กรมีรายการป้ายแล้ว เคสที่ติดหลายป้ายนับในทุกป้าย สัดส่วนรวมจึงเกิน 100% ได้ และเคสที่ไม่มีป้ายอยู่ในแถว "ยังไม่ติดป้าย"

ช่องแบบตัวเลือกเรียงตามลำดับตัวเลือกที่ตั้งไว้ ตามด้วยแถว "ยังไม่กรอก" ช่องแบบติ๊กแยกเป็น ใช่ กับ ไม่ใช่ ช่องแบบข้อความ ตัวเลข และวันที่ไม่อยู่ในมิติ เพราะค่าต่างกันเกือบทุกเคส ใช้ตัวกรองในหน้ารายการเคสหรือไฟล์ส่งออกแทน

**ตัวเลข** แบ่งเป็น 2 ชุด เลือกที่ปุ่มใต้มิติ ตารางจึงไม่กว้างเกินหน้าจอ จำนวนเคสและสัดส่วนอยู่ทั้งสองชุด

| ชุด | คอลัมน์ |
|---|---|
| ความเร็ว | ตอบครั้งแรก (ค่ากลาง และ 9 ใน 10 เคส) ตอบทัน SLA รอคำตอบถัดไป (ค่ากลาง) และแก้ไขเสร็จ (ค่ากลาง) |
| คุณภาพและความรู้สึก | แก้จบในครั้งเดียว เปิดซ้ำ CSAT และลูกค้าไม่พอใจ |

- กดหัวคอลัมน์เพื่อเรียง เช่น เรียงตามลูกค้าไม่พอใจ เพื่อดูว่าหมวดไหนหรือป้ายไหนทำให้ลูกค้าไม่พอใจที่สุด
- ดาวน์โหลดตารางเป็น CSV ไฟล์มีทุกคอลัมน์ของทั้งสองชุด
- ช่องที่มีไม่ถึง 3 เคสแสดงเป็นสีจาง เพราะยังใช้ตัดสินอะไรไม่ได้
- แถบคำใบ้บอกกลุ่มที่ตอบทัน SLA ต่ำที่สุด

## ส่งออกข้อมูล

| ไฟล์ | ใครดาวน์โหลดได้ | มีอะไร |
|---|---|---|
| CSV ของเคส | ทุกคน | เคสในช่วงที่เลือก ตามตัวกรอง |
| CSV ของตารางแยกมิติ | ทุกคน | ตารางที่แสดงอยู่ |
| ชุดข้อมูลสำหรับวิเคราะห์ (ZIP) | เจ้าขององค์กร | ตารางแยกตามชนิดสำหรับ Python, R, Excel, Power BI หรือ Looker Studio |

**ชุดข้อมูลสำหรับวิเคราะห์** มี CSV หนึ่งไฟล์ต่อชนิดข้อมูล เชื่อมกันด้วย id พร้อมคำอธิบายทุกคอลัมน์

- เคสที่เปิดในช่วงนั้น พร้อมเวลา ผล SLA และป้ายเคส
- บทสนทนาที่เริ่มในช่วงนั้น
- ข้อความเป็นเหตุการณ์ (เวลา ผู้เขียนเป็นแบบไหน ความยาว ไฟล์) ไม่มีเนื้อความ
- คะแนนความพึงพอใจ ไม่มีความคิดเห็น
- การเปิดซ้ำ การยกระดับ ทีม และสมาชิกที่ถูกอ้างถึง
- ลูกค้าปรากฏเป็นรหัสสุ่มเท่านั้น ไม่มีชื่อ อีเมล เบอร์โทร หรือข้อความ
- เวลาเป็น UTC แบบ ISO 8601

## พิมพ์หรือบันทึก PDF

ปุ่ม **พิมพ์หรือบันทึก PDF** ที่หัวหน้าเปิดหน้าพิมพ์ของเบราว์เซอร์ เลือกเครื่องพิมพ์ หรือ "บันทึกเป็น PDF" ไว้ใช้ประชุม

- พิมพ์เฉพาะรายงาน ไม่มีเมนู แถบด้านบน ตัวกรอง และปุ่ม
- หัวกระดาษบอกช่วงวันที่ ชื่อองค์กร และเวลาที่พิมพ์
- พิมพ์บนพื้นขาวเสมอ แม้ใช้ธีมมืดอยู่ การ์ดไม่ถูกตัดครึ่งระหว่างหน้า ถ้าวางในหน้าเดียวได้
- พิมพ์ตามตัวกรองและชุดตัวเลขที่เลือกอยู่

## สรุปรายสัปดาห์ทางอีเมล

ทุกวันจันทร์ตั้งแต่ 8 โมง (เวลาไทย) เจ้าขององค์กรได้อีเมลสรุปสัปดาห์ที่แล้ว (จันทร์ถึงอาทิตย์) เทียบกับสัปดาห์ก่อน ไม่ใช้ AI จึงไม่กินโควตา

- เคสใหม่ ตอบทัน SLA ตอบครั้งแรก รอคำตอบถัดไป แก้จบในครั้งเดียว คะแนนความพึงพอใจ เปิดซ้ำ และลูกค้าไม่พอใจ พร้อมตัวเลขสัปดาห์ก่อนในวงเล็บ
- ข้อที่ตั้งเป้าขององค์กรไว้ บอกว่าถึงเป้าหรือยัง
- เคสที่ยังเปิดอยู่และที่เกิน SLA ตอนนี้ และลิงก์ไปหน้ารายงาน
- ส่งเมื่อเจ้าขององค์กรเปิดการแจ้งเตือนทางอีเมล และเลือก **สรุปรายงานประจำสัปดาห์** ไว้ ที่ ตั้งค่าบัญชี → การแจ้งเตือน หน้ารายงานบอกเจ้าขององค์กรว่าเปิดอยู่หรือยัง
- ส่งสัปดาห์ละครั้งต่อองค์กร สัปดาห์ที่ไม่มีเคสเลยทั้งสองสัปดาห์และไม่มีเคสค้าง ไม่ส่ง
- ส่งผ่านอีเมลกลางของแพลตฟอร์ม แบบเดียวกับอีเมลแจ้งเตือนอื่นของทีมงาน
