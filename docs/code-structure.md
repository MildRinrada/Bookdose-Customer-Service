# โครงสร้างโค้ด

เอกสารนี้บอกว่าโค้ดแต่ละส่วนอยู่ที่ไหน แบ่งหน้าที่อย่างไร และกติกาที่ทุกคนต้องทำตามเมื่อเพิ่มหรือแก้ฟีเจอร์

## โฟลเดอร์หลัก

```text
app.py                  จุดเริ่มของ API: python app.py, --backup, --restore
config/settings.py      ค่าตั้งจากตัวแปรแวดล้อมหรือไฟล์ .env
requirements.txt        แพ็กเกจ Python (ตรึงรุ่น)
render.yaml             ตั้งค่าบริการบน Render
Start Bookdose.bat      เปิดระบบบน Windows
Start Bookdose.command  เปิดระบบบน macOS
backend/                API
frontend/               หน้าเว็บ Next.js
tests/                  ชุดทดสอบของ API
scripts/check.py        ตรวจ syntax, type, lint และรันชุดทดสอบ
integrations/n8n/       workflow ของ n8n สำหรับใช้เป็น AI ขององค์กร
docs/                   เอกสาร
data/                   ข้อมูลจริง (ไม่อยู่ใน Git)
```

## ฝั่ง API (backend/)

```text
backend/
  asgi.py        FastAPI: route เดียวรับทุกคำขอ แล้วส่งให้ dispatch
  server.py      เซิร์ฟเวอร์รุ่นเก่า (http.server) ไว้ย้อนกลับเท่านั้น
  workers.py     เริ่มและหยุดงานเบื้องหลัง
  http/          dispatch.py: ตาราง route และลำดับ middleware ตามระดับสิทธิ์
                 adapter.py: object req ของคำขอจาก ASGI
  middleware/    security.py: header และ Host/Origin
                 auth.py: ตัวตน CSRF และบทบาท
                 access.py: ขอบเขตทีมของเจ้าหน้าที่
                 rate_limit.py: จำกัดความถี่คำขอ
  realtime/      WebSocket ดู docs/realtime.md
  database/      db.py: การเชื่อมต่อ SQLite
                 schema.py: สร้างตารางจาก model ของทุกโมดูล
                 audit.py: ประวัติการทำงาน
                 backup.py: สำรองและกู้คืน
                 seed.py: ข้อมูลตัวอย่าง
  exceptions/    errors.py: ชนิด error ทั้งหมด
                 handlers.py: แปลงเป็น HTTP status
  extensions/    บริการภายนอก: LINE Meta อีเมล OpenAI Gemini n8n SMS Turnstile
                 และหน้าตาอีเมลที่ส่งออก (mail_style.py)
  utils/         ตัวช่วยที่ใช้ซ้ำ: validation วันเวลา ไฟล์ การเข้ารหัส Markdown QR code
  modules/       หนึ่งโฟลเดอร์ต่อหนึ่งฟีเจอร์
```

### ชั้นของโค้ดในแต่ละโมดูล

**routes → controller → service → repository → database**

| ไฟล์ | หน้าที่ | ห้ามทำ |
|---|---|---|
| `routes.py` | รายการ endpoint: method, URL, controller และระดับสิทธิ์ | มี logic หรือ query |
| `controller.py` | รับคำขอ เรียก service และส่งคำตอบ (status, cookie, ไฟล์ดาวน์โหลด) | มีกฎธุรกิจ |
| `service.py` | กฎธุรกิจทั้งหมด เรียก repository หรือ service ของโมดูลอื่น | รู้จัก HTTP |
| `repository.py` | query ฐานข้อมูลและไฟล์บนดิสก์ | มีกฎธุรกิจ |
| `model.py` | ตารางและค่าที่อนุญาต | ไม่มี |
| `schema.py` | ตรวจข้อมูลที่ส่งเข้ามา และจัดรูปข้อมูลที่ส่งกลับ | ไม่มี |

ไฟล์ไหนไม่มีเนื้อหาไม่ต้องสร้าง เช่น `portal` ไม่มีตารางของตัวเองจึงไม่มี `model.py` ฟีเจอร์ย่อยที่ใหญ่พอแยกเป็นไฟล์ของตัวเองในโมดูลเดียวกันได้ เช่น `organization/hours.py`

## ฝั่งหน้าเว็บ (frontend/)

```text
frontend/
  next.config.ts        ส่งต่อ /api/* ไปที่ API และ header ของหน้าเว็บ
  public/               ไฟล์สาธารณะ: โลโก้ widget.js รูปหน้าเข้าสู่ระบบ
  src/
    proxy.ts            ทำงานก่อนทุกคำขอ: CSP nonce, header ถึง API, กรอบของหน้าแชทแบบฝัง, กับดัก
    app/                URL ของทุกหน้าจอ (บาง: อ่าน params แล้วเรียก screen)
      (auth)/           เข้าสู่ระบบ สมัคร ตั้งค่าครั้งแรก ลืมรหัสผ่าน คำเชิญ
      (staff)/          หน้าของทีมงานและคอนโซลระบบกลาง
      customer/(portal) หน้าของลูกค้าที่เข้าสู่ระบบ
      customer/(link)   หน้าจากลิงก์ในอีเมลของลูกค้า
      support/          หน้าช่วยเหลือขององค์กรสำหรับผู้เยี่ยมชม
      status/           หน้าสถานะระบบ เปิดได้โดยไม่ต้องเข้าสู่ระบบ
    features/<ชื่อ>/    หนึ่งโฟลเดอร์ต่อหนึ่งฟีเจอร์
    components/         UI กลาง: Icon, ui/ (ฟอร์ม กล่องโต้ตอบ ตัวกรอง ตาราง), shell/ (กรอบหน้าจอ)
    lib/                client เรียก API, เซสชัน, URL, realtime, คำภาษาไทย, จัดรูปแบบ
    styles/             CSS ทั้งหมด โหลดตามลำดับใน app/layout.tsx
```

### ชั้นของโค้ดในแต่ละฟีเจอร์

| ชั้น | ไฟล์ | หน้าที่ | คู่กับฝั่ง API |
|---|---|---|---|
| Route | `src/app/**/page.tsx` | URL ของหน้าจอ อ่าน params แล้วเรียก screen | `routes.py` |
| Screen | `features/<ชื่อ>/*Screen.tsx` | ประกอบหน้าจอ อ่านข้อมูล จัดการ state และเรียก action | `controller.py` |
| Component | `features/<ชื่อ>/components/` | ชิ้นส่วนแสดงผลของฟีเจอร์ | ไม่มี |
| API | `features/<ชื่อ>/api.ts` | ฟังก์ชันเรียก endpoint ของฟีเจอร์ | `routes.py` และ `schema.py` |
| Types | `features/<ชื่อ>/types.ts` | รูปข้อมูลที่ API ส่งกลับ ชื่อฟิลด์ snake_case ตาม API | `schema.py` |
| Labels | `features/<ชื่อ>/labels.ts` | คำภาษาไทยและกติกาเล็ก ๆ ของฟีเจอร์ | ไม่มี |

ชื่อโฟลเดอร์ฟีเจอร์ตั้งให้ตรงกับโมดูลฝั่ง API เท่าที่ทำได้

## กติกาการเขียนโค้ด

### ทั้งสองฝั่ง

1. **คำบนหน้าจอเป็นภาษาไทย** คอมเมนต์และชื่อตัวแปรเป็นภาษาอังกฤษ ดูกติกาภาษาใน [การออกแบบ UI/UX](ui-ux.md)
2. **คอมเมนต์หัวไฟล์บอกว่าไฟล์นี้ทำอะไรและทำไม** ใช้ภาษาธรรมดา ไม่ใช่รายการฟังก์ชัน
3. **เขียนให้เหมือนโค้ดรอบข้าง** ทั้งความหนาแน่นของคอมเมนต์ การตั้งชื่อ และรูปแบบ

### ฝั่ง API

1. **สิทธิ์ตรวจที่ API เสมอ** ข้อมูลที่ผู้ใช้ไม่มีสิทธิ์เห็นตอบ 404 ไม่ใช่ 403 จึงไม่บอกว่ามีอยู่จริง
2. **ตรวจข้อมูลเข้าด้วย `require(เงื่อนไข, 'ข้อความภาษาไทย', status)`** ข้อความ error เป็นภาษาไทยที่ผู้ใช้อ่านเข้าใจ
3. **ไม่เรียกบริการภายนอกระหว่างเปิด transaction**
4. **การปรับฐานข้อมูลเป็นแบบเพิ่มอย่างเดียว** เพิ่มตารางหรือคอลัมน์ใน `model.py` ห้ามลบหรือเปลี่ยนความหมายของคอลัมน์เดิม
5. **ใช้ standard library เป็นหลัก** ถ้าจำเป็นต้องเพิ่มแพ็กเกจ ต้องตรึงรุ่นใน `requirements.txt`
6. **การเปลี่ยนแปลงสำคัญบันทึกลงประวัติการทำงาน** ด้วย `audit.record(...)` ไม่บันทึกรหัสผ่าน token หรือเนื้อความ

### ฝั่งหน้าเว็บ

1. **อ่านข้อมูลด้วย `useApi<T>(path)` เท่านั้น** key ของ cache คือ path หน้าจอที่ต้องอัปเดตเองใช้ `{ refetchInterval: useRealtimeInterval(ms) }`
2. **แก้ข้อมูลผ่านฟังก์ชันใน `features/<ชื่อ>/api.ts`** แล้ว `await refresh(path)` จาก `useInvalidate()` ห้ามเรียก `fetch` ตรง
3. **ฟอร์มใช้ `<Form onSubmit>`** กับ `TextField`, `TextArea`, `SelectField`, `Combobox`, `FileInput` error ที่ throw แสดงบนฟอร์มเอง และปุ่มส่งถูกปิดระหว่างส่ง
4. **กล่องโต้ตอบใช้ `useDialogs()`** และข้อความสั้นใช้ `useToast()` ห้ามใช้ `alert`, `confirm`, `prompt` ของเบราว์เซอร์
5. **ห้ามใช้ `style={...}`** เพราะ CSP ของ production ไม่อนุญาต inline style ใช้ class ใน `src/styles`, `<progress>`, attribute ของ SVG หรือ `element.style.setProperty` แทน
6. **ห้ามใช้ `dangerouslySetInnerHTML`** ยกเว้นตัวแปลง Markdown กลางที่ escape ทุกอย่างก่อน
7. **สิทธิ์ตามบทบาทกำหนดใน `lib/routes.ts`** ปุ่มที่เฉพาะบางบทบาทซ่อนด้วย `useWork().role` แต่ API ยังตรวจเองทุกคำขอ

## เพิ่มฟีเจอร์ใหม่

**ฝั่ง API**

1. สร้าง `backend/modules/<ชื่อ>/` พร้อมไฟล์ที่ต้องใช้
2. ประกาศตารางใน `model.py` และให้ `backend/database/schema.py` รู้จัก
3. เพิ่ม route ใน `routes.py` เลือกระดับสิทธิ์ให้ถูก
4. ถ้ามีงานเบื้องหลัง ให้เรียกจาก worker ที่มีอยู่ ไม่สร้าง thread ใหม่เอง
5. เขียนเทสต์ใน `tests/test_<ชื่อ>.py`

**ฝั่งหน้าเว็บ**

1. สร้าง `frontend/src/features/<ชื่อ>/` พร้อม `api.ts`, `types.ts` และ screen
2. เพิ่ม `page.tsx` ใน `src/app/` ให้เรียก screen
3. ถ้าเป็นเมนูใหม่ เพิ่มใน `lib/routes.ts`
4. เพิ่ม CSS ใน `src/styles/pages/` แล้ว import ใน `app/layout.tsx`
5. ตรวจด้วย `npm run typecheck` และ `npm run lint`

## ชุดทดสอบ

- `tests/test_*.py` ยิงคำขอ HTTP จริงไปที่เซิร์ฟเวอร์ที่เปิดในเทสต์ ใช้โฟลเดอร์ข้อมูลชั่วคราว
- `tests/*_fixture_server.py` จำลองบริการภายนอก
- ไฟล์เทสต์ใหม่ยืม setUp และตัวช่วยของ `test_app.IntegrationTests` ได้ ดูตัวอย่างท้ายไฟล์ `tests/test_org_profile.py`
