# ขอบเขตระบบ Customer Service

ระบบบริการลูกค้าบนเว็บสำหรับหลายองค์กร เน้น **แชท เคส และถามตอบ (Q&A)** เอกสารนี้สรุปว่าใครใช้ส่วนไหน ทำอะไรได้แล้ว
อะไรยังขาด และลำดับงานต่อไป ปรับปรุงล่าสุด 16 กันยายน 2026 หลังตกลงขอบเขตใหม่

**สัญลักษณ์สถานะ**

| สัญลักษณ์ | ความหมาย |
|---|---|
| ✅ | ทำเสร็จแล้ว ใช้งานได้จริง และมีชุดทดสอบอัตโนมัติ |
| 🔄 | กำลังพัฒนา |
| ⬜ | ยังไม่ได้ทำ (ดูลำดับในหัวข้อ 7) |

**สิ่งที่อยู่นอกขอบเขต (ไม่ทำเด็ดขาด)**

ทุกอย่างที่เกี่ยวกับเงินและสัญญา ได้แก่ TOR, สัญญา, ใบเสนอราคา, ใบแจ้งหนี้, ใบเสร็จ/ใบกำกับภาษี, การชำระเงินและสลิป,
งบประมาณ, ค่าจ้าง, งวดงานและการตรวจรับ, ประกัน/MA, ปฏิทินกำหนดการ (ICS), คลังเอกสารโครงการ, ขั้นตอนอนุมัติเอกสาร
และการเก็บเงินจากองค์กร โค้ดส่วนเหล่านี้ถูกลบออกแล้ว (สำรองไว้ที่ branch `backup/before-scope-cut`)

## 1. ผู้ใช้ระบบ

| Role | คือใคร | ใช้ระบบทำอะไร |
|---|---|---|
| **Superadmin** | ผู้ดูแลเซิร์ฟเวอร์และแพลตฟอร์ม | ดูแลองค์กรทั้งหมด สุขภาพระบบ ทีมผู้ดูแล และ FAQ กลาง |
| **องค์กรทั่วไป** | ผู้ให้บริการที่มีลูกค้าของตัวเอง (ผู้ดูแล หัวหน้าทีม เจ้าหน้าที่) | รับเรื่องจากทุกช่องทาง ตอบแชท จัดการเคส ดูแลคลังความรู้ |
| **ลูกค้าขององค์กร** | ผู้ที่ติดต่อองค์กร | ถาม แจ้งปัญหา ติดตามเรื่อง และให้คะแนนบริการ |

**ลูกค้ามี 2 แบบ**

| แบบ | เข้าถึงอย่างไร | สถานะ |
|---|---|---|
| เข้าสู่ระบบ | บัญชีเดียวติดต่อได้หลายองค์กร ผ่านลิงก์ รหัสองค์กร หรือ QR | ✅ |
| ไม่เข้าสู่ระบบ ผ่าน LINE / Facebook / อีเมล | ระบบจำตัวตนจากช่องทางนั้นเอง | ✅ |
| ไม่เข้าสู่ระบบ ผ่านเว็บ | เริ่มแชทได้ทันที ติดตามต่อด้วยเบราว์เซอร์เดิม ลิงก์ทางอีเมล/SMS หรือ LINE (หัวข้อ 4.1) | ✅ |

## 2. สถาปัตยกรรม

```text
เบราว์เซอร์ ──► Next.js (frontend/, :3000) ──/api/*──► FastAPI (app.py, :8787) ──► SQLite
                หน้าจอ + CSP ต่อคำขอ        proxy       routes → controller → service → repository
```

| ส่วน | ตอนนี้ | แผน |
|---|---|---|
| หน้าเว็บ | Next.js 16 + React 19 + TypeScript | คงเดิม |
| เซิร์ฟเวอร์ | **FastAPI บน uvicorn** (worker เดียว) ใช้ route, middleware, controller, service และ repository เดิมผ่าน `backend/http/dispatch.py` ส่วนอื่นใช้ Python standard library · `http.server` เดิมเก็บไว้ย้อนกลับด้วย `BOOKDOSE_SERVER=legacy` | ✅ ระยะที่ 1 เสร็จ · ⬜ ระยะที่ 2: router ของ FastAPI จริงทีละโมดูล (แผนใน `docs/FASTAPI-MIGRATION.md`) |
| ฐานข้อมูล | SQLite แยกไฟล์ต่อองค์กร + ฐานกลาง | ⬜ พิจารณา PostgreSQL เมื่อผู้ใช้มากขึ้น |

**การแยกข้อมูลระหว่างองค์กร:** ทุกคำขอผูกกับฐานข้อมูลขององค์กรที่ทำงานอยู่ ข้ามองค์กรไม่ได้ และทีมแพลตฟอร์มต้องขอสิทธิ์
เข้าช่วยเหลือเป็นครั้ง ๆ

## 4. สิ่งที่ยังขาด

### 4.1 ลูกค้าที่ไม่เข้าสู่ระบบบนเว็บ (✅ เสร็จแล้ว)

| สถานะ | สิ่งที่ทำ | รายละเอียด |
|---|---|---|
| ✅ | **หน้าแชทสาธารณะ `/chat/<รหัสองค์กร>`** | เริ่มแชทได้โดยไม่ต้องสมัคร ใช้ AI ช่วยตอบ แนบไฟล์ และให้คะแนนได้เหมือนลูกค้าที่เข้าสู่ระบบ |
| ✅ | **จำในเบราว์เซอร์นี้** | cookie แบบ HttpOnly อายุต่ออัตโนมัติเมื่อใช้งาน (เครื่องเดียว) ปิดได้สำหรับเครื่องสาธารณะ |
| ✅ | **ลิงก์ติดตามทางอีเมลหรือ SMS** | ลิงก์ลับอายุ 30 วัน ใช้ได้ 20 ครั้ง ลิงก์ใหม่ยกเลิกลิงก์เก่า token อยู่หลัง `#` ไม่ติด log · SMS ยังเป็นโครง (ปิด / ทดสอบ) รอเลือกผู้ให้บริการ |
| ✅ | **แจ้งเตือนทาง LINE** | ส่งรหัส 6 หลักใน LINE OA ขององค์กร แจ้งเตือนเฉพาะช่องทางที่ยืนยันแล้ว ไม่ส่งเนื้อหาข้อความ |
| ✅ | **รวมประวัติเข้าบัญชี** | อัตโนมัติเมื่ออีเมลที่ยืนยันตรงกัน หรือกดย้ายเองจากแบนเนอร์เมื่อเข้าสู่ระบบในเบราว์เซอร์เดิม |
| ✅ | **โค้ดฝังบนเว็บองค์กร** | `widget.js` ปุ่มลอย + หน้าต่างแชท อนุญาตเฉพาะโดเมนที่องค์กรตั้ง (frame-ancestors) ตั้งค่าที่ ตั้งค่าองค์กร → แชทบนเว็บไซต์ |
| ✅ | **ป้ายผู้เยี่ยมชมในกล่องข้อความ** | เจ้าหน้าที่เห็นว่าเป็นผู้เยี่ยมชมและติดต่อกลับทางไหนได้ |

กันสแปม: ช่องดักบอท, ตรวจเวลากรอกฟอร์ม, จำกัดแชทใหม่ต่อ IP และต่อผู้เยี่ยมชม, จำกัดการขอลิงก์ต่อผู้รับและต่อ IP

## 5. ความปลอดภัย

### 5.1 ที่ทำแล้ว (✅)

**บัญชีและการยืนยันตัวตน**
- 2FA ด้วยแอป Authenticator พร้อมรหัสสำรอง 10 ชุด
- Passkey (ลายนิ้วมือ ใบหน้า PIN ของอุปกรณ์)
- เปิด 2FA หรือเพิ่ม Passkey ต้องยืนยันรหัสผ่านก่อน และการตั้งรหัสผ่านใหม่ล้าง Passkey เดิม
- เปลี่ยนรหัสผ่านแล้วอุปกรณ์อื่นออกจากระบบ, รายการอุปกรณ์ และปุ่มออกจากระบบทุกเครื่อง
- ประวัติการใช้งานบัญชี

**การเข้าถึงข้อมูล**
- ฐานข้อมูลแยกต่อองค์กร ตรวจสิทธิ์ทุกคำขอที่เซิร์ฟเวอร์
- ทีมแพลตฟอร์มต้องขอสิทธิ์เข้าช่วยเหลือเป็นครั้ง ๆ

**หน้าเว็บและการส่งข้อมูล**
- CSP พร้อม nonce ต่อคำขอ ไม่มี inline script/style
- Escape ข้อความผู้ใช้ทั้งหมด ไฟล์แนบตรวจทั้งนามสกุลและไบต์จริง
- Cookie HttpOnly + SameSite=Strict, ตรวจ CSRF และ Host/Origin
- จำกัดจำนวนคำขอ แยกการอ่านกับการเขียน, ไม่มี token ใน URL
- ล็อกบัญชีแบบเพิ่มเวลาเมื่อกรอกรหัสผิดซ้ำ (5 ครั้ง/15 นาที → 5 นาที, 15 นาที, 1 ชม., 24 ชม.) ตอบเหมือนกันทั้งอีเมลที่มีและไม่มีบัญชี นับรหัส 2FA/รหัสสำรองของลูกค้าด้วย ปลดล็อกเมื่อครบเวลา ตั้งรหัสผ่านใหม่ หรือผู้ดูแลแพลตฟอร์มปลดให้
- อายุเซสชันแบบไม่ใช้งาน + อายุสูงสุด (เจ้าหน้าที่ 60 นาที/12 ชม., ผู้ดูแลแพลตฟอร์ม 30 นาที/8 ชม., ลูกค้า 7/30 วัน ปรับได้) การดึงข้อมูลเบื้องหลังและ WebSocket ไม่ต่ออายุ
- บันทึกเหตุการณ์ความปลอดภัย (90 วัน) กฎแจ้งเตือนทุกนาที อีเมลแจ้งผู้ดูแลเมื่อวิกฤต และบล็อก IP ทั้ง HTTP และ WebSocket
- กับดัก Honeypot (เส้นทางล่อทั้ง API และหน้าเว็บ ช่องซ่อนในฟอร์มเข้าสู่ระบบ/สมัคร/ลืมรหัสผ่าน/แชทผู้เยี่ยมชม) และ Honeytoken (อีเมลบัญชีล่อ API key รหัสผ่าน ลิงก์ไฟล์) ตอบเหมือนปกติทุกกรณี บันทึกเหตุการณ์ แจ้งเตือนวิกฤต และบล็อก IP อัตโนมัติ

### 5.2 ที่วางแผนไว้ (⬜)

| ลำดับ | เรื่อง |
|---|---|
| ✅ | ล็อกบัญชีแบบเพิ่มเวลาเมื่อกรอกรหัสผิดซ้ำ และจำกัดอายุ session (ย้ายไป 5.1) |
| ✅ | Honeypot / Honeytoken เพื่อจับพฤติกรรมผิดปกติแต่เนิ่น ๆ (ย้ายไป 5.1) |
| P2 | วิเคราะห์พฤติกรรมผู้ใช้และอุปกรณ์ (UEBA) |

## 6. ข้อจำกัดที่ทราบ

| เรื่อง | สถานะ |
|---|---|
| การส่งอีเมล | ยังไม่ได้ตั้งกล่องจดหมายกลาง จึงยังไม่ส่งอีเมลแจ้งเตือนและลิงก์ติดตามแชท |
| SMS | ยังไม่ได้เลือกผู้ให้บริการ มีเฉพาะโหมดทดสอบที่เขียนลิงก์ลง log (ห้ามใช้กับลูกค้าจริง) |
| Widget บน Safari | Safari อาจบล็อก cookie ใน iframe ผู้เยี่ยมชมจะถูกนับเป็นคนใหม่ทุกครั้ง (หน้าเต็ม `/chat/...` ไม่มีปัญหา) |
| LINE | องค์กรต้องเชื่อม LINE Official Account ก่อนจึงแจ้งเตือนเข้า LINE ได้ |
| ฐานข้อมูล | SQLite รองรับการเขียนพร้อมกันได้จำกัด |
| ตารางเก่า | ฐานข้อมูลเดิมยังมีตารางของฟีเจอร์ที่ลบไปแล้ว ระบบไม่ใช้และไม่ลบข้อมูลทิ้งเอง |
| การนำขึ้นใช้งานจริง | มีไฟล์ตั้งค่า Render แต่ยังไม่ได้ทดสอบบนระบบจริง |
